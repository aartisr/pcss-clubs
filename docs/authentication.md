# PCSS sign-in and authorization

The portal uses an OpenID Connect issuer chosen at deployment time. Public pages remain readable without signing in. Puck and registry edit controls require an authorized server session. The integration uses Authorization Code with PKCE, state, and nonce; the server verifies the ID token and sets a short lived, encrypted, HttpOnly, SameSite cookie. Browser JavaScript receives a name and email for display, never provider tokens.

## Google Workspace: `pcss2robotics@pioneercss.org`

Use this path if that address is an actual Google Workspace user account that can sign in. A Google Group, alias, or shared inbox cannot necessarily sign in as that address; ask the school Workspace administrator to confirm the account type and primary sign-in email. If it is an alias, allowlist the primary address returned in the Google ID token, or use the stable `sub` identifier after verifying the account. Avoid sharing one account among many editors when individual school accounts are available.

1. Ask the school's Google Workspace/Cloud administrator to create or select a **school-owned Google Cloud project**. Configure its branding using the exact [PCSS branding fields below](#pcss-branding-for-googles-sign-in-screen). Under **Audience**, choose **Internal** if available. Internal requires a project owned by the Workspace organization; if unavailable, use **External** with this account added as a test user while evaluating, and ask the administrator about the correct publication path. The app requests only `openid profile email` for sign-in, not Gmail, Drive, or other data access.
2. In **Google Auth platform → Clients**, create a client with application type **Web application**. Register the exact redirect URI for each environment being enabled: `http://localhost:3000/api/auth/callback`, `https://staging.pcssclubs.org/api/auth/callback`, and `https://pcssclubs.org/api/auth/callback`. Separate clients for local, staging, and production keep their secrets independent. The client uses server-side Authorization Code flow; it does not need a browser JavaScript origin for token exchange. Record the client ID and client secret privately.
3. For local development, copy `.env.example` to `.env.local` and set the following values, replacing the client credentials and session secret. Generate the secret with the command shown in `.env.example`. Do not commit `.env.local`.

   ```dotenv
   OIDC_ISSUER=https://accounts.google.com
   OIDC_CLIENT_ID=YOUR_GOOGLE_WEB_CLIENT_ID
   OIDC_CLIENT_SECRET=YOUR_GOOGLE_WEB_CLIENT_SECRET
   OIDC_APP_ORIGIN=http://localhost:3000
   OIDC_SESSION_SECRET=YOUR_32_BYTE_BASE64URL_SECRET
   OIDC_ALLOWED_EMAILS=pcss2robotics@pioneercss.org
   OIDC_REQUIRED_HOSTED_DOMAIN=pioneercss.org
   ```

4. Run `npm run dev`. Open `http://localhost:3000/editor/home`, select the `pcss2robotics@pioneercss.org` account in Google's chooser, and complete the school's normal sign-in or MFA. The page should return to the editor. Open `/api/auth/session` in the same browser: `configured` and `canEdit` should both be `true`. In a private browser window, public pages should work while the editor asks for sign-in. Try a different school account: it should not gain edit access.
5. In **Vercel → Project → Settings → Environment Variables**, set the same names for **Production**, changing `OIDC_APP_ORIGIN` to the one public host that actually serves the site after Vercel's domain redirects. Put `OIDC_CLIENT_SECRET` and `OIDC_SESSION_SECRET` in **Secret** variables. Use a fresh session secret and the production client ID/secret. Redeploy after saving variables. `npm run build` fails on Vercel Production when these required settings are absent or malformed. Vercel may report `pcssclubs.ai-aarti.com` as its production URL; that system-selected domain does not replace the portal's chosen sign-in host. Configure `pcssclubs.org` and `www.pcssclubs.org` in Vercel Domains with only one redirect direction; never add a reverse redirect in `vercel.json` or the page. The Google callback must use the destination host exactly. For staging, repeat with a separate Preview or Custom Environment configuration, `https://staging.pcssclubs.org`, and its matching client. Unique Preview URLs require their own exact registered callback; leave editor sign-in off on unregistered previews.
6. Test on the actual production domain: visit `https://pcssclubs.org/editor/home`, sign in, edit a harmless local draft, sign out, and check that another account is denied. If Google shows `redirect_uri_mismatch`, compare the browser URL, `OIDC_APP_ORIGIN`, and registered redirect URI character for character. If Google shows `admin_policy_enforced`, ask the Workspace administrator to allow the app. If the site says access denied, verify the returned account's email is the allowlisted address and its Workspace hosted domain is `pioneercss.org`.

The `hd` authorization parameter helps Google show the right account chooser, but the server enforces the signed `hd` claim from the validated ID token. The email allowlist also requires `email_verified=true`. Google recommends using `sub` as the lasting account identifier; after a successful test, an administrator can add its stable value to `OIDC_ALLOWED_SUBJECTS` if account renames or aliases are expected. Keep `OIDC_REQUIRED_HOSTED_DOMAIN` in place for school-only access. See [Google OIDC](https://developers.google.com/identity/openid-connect/openid-connect), [Google's backend identity guidance](https://developers.google.com/identity/sign-in/web/backend-auth), [OAuth consent setup](https://developers.google.com/workspace/guides/configure-oauth-consent), [OAuth client setup](https://developers.google.com/workspace/guides/create-credentials), and [Vercel environment variables](https://vercel.com/docs/environment-variables).

## Set up an identity provider

1. Create a **confidential web application** in your school identity provider. Require OIDC discovery, Authorization Code, PKCE S256, and a client secret. Enable the `openid`, `profile`, and `email` scopes. Use a trusted issuer with HTTPS.
2. Register one exact callback per environment: `http://localhost:3000/api/auth/callback` for local development, `https://staging.pcssclubs.org/api/auth/callback` for staging, and `https://pcssclubs.org/api/auth/callback` for production. Make separate provider applications and secrets for each environment. For unique Vercel Preview URLs, either register each exact URL or leave editing disabled there; wildcard redirects are inappropriate.
3. Copy `.env.example` to an ignored `.env.local` locally. Set `OIDC_ISSUER` to the exact issuer URL in discovery metadata, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`, `OIDC_APP_ORIGIN`, and a fresh `OIDC_SESSION_SECRET` of 32 random bytes encoded as base64url. The default token endpoint authentication is `client_secret_post`; set `OIDC_CLIENT_AUTH_METHOD=basic` if the provider requires `client_secret_basic`. Vercel receives these as server-side environment variables, never `VITE_` variables. Use a different session secret per environment.
4. Choose who can edit. `OIDC_ALLOWED_SUBJECTS` is a comma-separated list of stable provider subject IDs. `OIDC_ALLOWED_EMAILS` is a comma-separated list of email addresses; an email is accepted only when the provider marks it verified. For Google Workspace, set `OIDC_REQUIRED_HOSTED_DOMAIN` to the expected signed `hd` claim. If *every* account from the issuer is an approved editor, explicitly set `OIDC_EDIT_POLICY=authenticated`. With no allowlist and no such policy, all sign-ins are denied.
5. Run `npm run dev`, visit an `/editor/` link, and sign in. The login returns to the requested editor. Confirm that a visitor can still browse public pages, that an unlisted account cannot edit, and that signing out closes the editor. Repeat on staging before production.

Google Cloud project administrators do not automatically have this app role.

The full research, experience design, and phased delivery plan are in [School-member experience research and plan](member-experience-research-and-plan.md).

**Current limitation:** The app does not yet have a school-member session or role. A school account outside the editor allowlist is redirected to `/?auth=denied` after sign-in and has the same site access as a public visitor. For future member features, identify an account by Google's stable `sub` claim and check the signed `hd` claim before granting school-member access. Keep editor permission as a separate allowlist. ## User experience

- An editor link opens a clear sign-in screen and remembers the destination. A signed-in editor goes straight to Puck.
- Public pages show Edit links, directory management controls, and the Puck builder link only while the session reports `canEdit`. The Sign in control remains available when authentication is configured.
- A provider configuration error or network failure shows a retryable state. The editor stays closed.
- A failed or cancelled provider callback returns to a plain-language notice while preserving the original local task for retry. Direct sign-in links with missing provider setup show a readable unavailable state. A temporary account-check failure keeps **Sign in** available; selecting it checks the session again and starts Google sign-in only if the check succeeds. If the check fails again, the site shows **Try sign-in again**, **Browse public clubs**, and **Get help** without losing the current page. The My space and editor entry pages also show direct public and support paths.
- Session lifetime is eight hours. A new login starts a fresh five minute transaction. Logout deletes the local session cookie.
- Up to four simultaneous sign-in attempts can coexist in the encrypted flow cookie. Completing or cancelling one removes only that attempt; an unrelated callback state cannot erase another tab's attempt.
- An existing valid Pioneer Clubs session goes straight to the requested page when `/api/auth/start` is opened; it does not start another Google authorization flow. A Google account session alone is different from the site's session cookie. Once the site session expires or is removed, Google may show its account/consent confirmation again. The app does not request `prompt=consent`, which would force the consent screen every time. Google's `prompt=none` can avoid a screen only when Google can authenticate the user and reuse prior consent without interaction; it returns an error otherwise, so it is not a reliable replacement for the normal sign-in flow. [Google OpenID Connect prompt behavior](https://developers.google.com/identity/openid-connect/openid-connect).

### Choosing another school account

Signing out clears the Pioneer Clubs session, but it does not end a Google or Chrome session. Google may otherwise select the same browser account on the next OAuth request. Google documents `prompt=select_account` for this case; it asks the person to choose an account without forcing a new consent grant. [Google OAuth prompt reference](https://developers.google.com/identity/protocols/oauth2/web-server), [Google session distinction](https://developers.google.com/identity/gsi/web/guides/migration).

The account menu has **Switch school account** on desktop and mobile. This starts a new authorization request with `prompt=select_account` even while a Pioneer Clubs session exists. The old session remains in place until an eligible new account completes sign-in. Cancelling or choosing an ineligible account leaves the old session in place and explains the result. Explicit sign-out sets an HttpOnly account-choice cookie; subsequent sign-in attempts request the Google account chooser until an eligible account completes sign-in, which clears the cookie. Ordinary first-time and returning sign-ins do not force the chooser. The account chooser is Google's UI; it may still offer an account already signed in to Google or trigger a school-managed Chrome profile prompt.

In local development, `npm run dev` watches and restarts the server when backend source changes. If an older dev process is already running, stop it and start `npm run dev` once to pick up the watch command. Restart after changing environment variables. Vite's browser refresh alone does not reload a previously running Express authentication handler.

The automated authentication path matrix in `tests/auth-paths.test.ts` exercises ordinary sign-in, repeat sign-in, explicit account switching, cancellation, provider and token failures, denied identities, successful replacement, sign-out and account-choice persistence, callback replay and state errors, session permissions, request methods, origins, and safe destinations. It uses a local mock OpenID Connect provider and signed test tokens. A final Google account-selection screen and Chrome profile prompt are controlled by Google and Chrome, so they require a manual browser check with the real school account.

### Recovering from a Google 400 during sign-in

The generic Google page saying **“400. The server cannot process the request because it is malformed”** does not identify a specific OAuth error. Google can show an error on its own page before redirecting to our callback; our UI cannot replace that page. In the November 22 screenshot, the browser address was a Google internal `/signin/oauth/id` URL and Chrome was simultaneously showing **“Making Chrome yours…”** after a work-profile prompt. A profile transition interrupting a sign-in is a plausible explanation, **not a proven diagnosis**. The local app's `/api/auth/start` was checked and generated a standard authorization-code request with PKCE, `openid profile email`, no forced `prompt`, and `http://localhost:3000/api/auth/callback` as its redirect URI. That check does not validate the production Google Cloud configuration or the user's Chrome profile.

**Immediate recovery:** Close the Google error tab. In the Chrome profile the student intends to keep, open the Pioneer Clubs origin again and start a *new* sign-in from the site. Do not reload or bookmark the long `accounts.google.com/signin/oauth/id?...` URL: it is an intermediate Google URL, not the app's sign-in entry. Avoid switching Chrome profiles mid-flow. If it repeats in a stable profile, record the **Pioneer Clubs hostname**, approximate time, whether this was a new Chrome profile, and Google's short error code if one appears. Never send the full Google URL, authorization code, cookies, or client secret in a support message.

**Operator checks if reproducible:** Compare the exact `redirect_uri` emitted for that environment with the authorized redirect URI on the Google OAuth web client referenced by that environment's `OIDC_CLIENT_ID`. Check scheme, host, port, path, and trailing slash. Confirm the OAuth project's audience/test-user settings and the school Workspace app access policy. Test the same account in a stable Chrome profile and another approved browser to separate browser-profile interruption from server/client configuration. Google's documented `redirect_uri_mismatch`, `invalid_request`, `org_internal`, and `admin_policy_enforced` errors require different fixes; do not treat a generic 400 screenshot as proof of any one of them. [Google OAuth error reference](https://developers.google.com/identity/protocols/oauth2/web-server), [Chrome managed-profile separation](https://support.google.com/chrome/a/answer/2657289).

**App recovery:** If Google redirects a failed or cancelled authorization attempt back to `/api/auth/callback`, the app now checks the transaction state, clears the temporary flow cookie, and returns the visitor to `/my` with a short explanation and retry action. It never automatically retries a failed login or turns an error into a signed-in session. A Google-hosted error page that never reaches our callback remains outside the app's control.

- Sign-in and logout work on the configured origin. Use the apex host for editor links if club subdomains are introduced; cookies are host-only.

## Security boundary and operations

`/api/auth/session` is a server assertion about the cookie. The Puck component is loaded only after it reports `canEdit`. The cookie is encrypted with AES-256-GCM and cannot be read by browser JavaScript. The OAuth transaction binds the browser cookie to state, nonce, and a PKCE verifier. The callback validates the ID token through `openid-client`. Redirect destinations must be relative paths. Logout checks the request origin.

**Current publishing limitation:** Puck and registry edits are stored in each browser's `localStorage`; there is no shared write API. This gate controls the supported editing interface, but client-side storage is under the browser owner's control. It does not turn local drafts into centrally secured or published content. Before adding a database or publish endpoint, enforce authorization inside every server write handler, add CSRF protection to those handlers, and add an audit trail. A locally deleted stateless session cookie cannot revoke a copied session token before its eight hour expiry; use a server-side session store if immediate revocation becomes a requirement.

For Vercel, keep `api/auth/*` functions deployed and set environment variables on the matching deployment environment. `OIDC_APP_ORIGIN` must match the host visitors use exactly. In Preview deployments with Vercel Deployment Protection, allow the identity provider callback to reach the protected deployment or use a staging host with an appropriate access policy. Test the actual full round trip after changing protection settings.

The auth function files use `.js` suffixes in relative imports even though their source is TypeScript. Vercel emits JavaScript for its Node runtime, and native ESM does not resolve extensionless relative imports. `npm run check:functions` removes stale emitted files, recompiles the four auth entries as Node ESM, checks their relative import targets, loads each entry with Node, and exercises unconfigured, misconfigured, anonymous, origin-rejection, logout, and sign-in handoff paths. This gate catches the production `ERR_MODULE_NOT_FOUND` class of failure that a Vite-only build misses. After deployment, verify `/api/auth/session` returns JSON before testing Google sign-in; a deployed function's module-loading behavior still requires a live check.

Local npm installation may use the internal corporate registry through the developer's npm configuration. The committed lockfile uses public npm package URLs so Vercel does not need corporate access.
