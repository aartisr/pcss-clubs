# Production sign-in recovery

## What the symptom establishes

The previous navigation rendered **Sign-in help** only when the browser's session check completed with `configured: false`. The server returns that response when at least one of `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`, `OIDC_APP_ORIGIN`, or `OIDC_SESSION_SECRET` is missing or empty. The client then replaced the sign-in action with a link to Support; My space and other protected flows also hid their sign-in action. This made a deployment setup failure appear to be a user navigation problem and left no useful retry on the page.

The local `.env.local` has all five required keys, passes `getAuthConfig`, and `http://localhost:3000/api/auth/session` returned `configured: true` on November 22, 2026. That does **not** establish the production configuration. This workspace cannot read the Vercel project's Production variables or reach the production endpoint through its corporate network proxy. The most direct production check is to open `https://pcssclubs.org/api/auth/session` in a browser that can reach the site. It must return JSON with `configured: true`. A response with `configured: false` confirms missing Production-scoped OIDC configuration. A 503 means malformed configuration or a function error; a 400 with `Invalid application origin` means the visited host differs from `OIDC_APP_ORIGIN`.

**Confirmed production finding:** A visitor opened `/api/auth/session` and received `Invalid application origin`. This is a mismatch between the request origin and `OIDC_APP_ORIGIN`. The client previously classified every non-2xx session response as a generic check failure; its retry sent the same request again and left the user on the same screen. No Google sign-in could start from that state.

**Confirmed redirect loop:** The failing request came from `https://www.pcssclubs.org`, while `OIDC_APP_ORIGIN` was set to `https://pcssclubs.org`. Vercel Domains redirects the apex to `www`. A later repository rule redirected `www` to the apex, so each host sent the browser back to the other. The repository rule and browser fallback have been removed locally. To restore the site immediately, change the Vercel Domains setting so `www.pcssclubs.org` redirects to `pcssclubs.org` and the apex serves the production deployment. Keep `OIDC_APP_ORIGIN=https://pcssclubs.org` and the Google callback on the apex. After publishing the repository rollback, Vercel remains the only place for host redirects. Test in a private browser window because 308 redirects may be cached. A live check should show one redirect at most, followed by a 200 page and `configured: true` from `/api/auth/session` on the apex.

**Fresh private-window `auth=failed` on the apex:** This confirms that the browser reached the app's callback, but does not identify which callback step failed. The existing code uses `auth=failed` for a state mismatch, a provider authorization error, a failed code exchange, or an identity-token validation exception. A missing or expired flow cookie normally yields `auth=expired`, so this symptom alone does not prove cookies were blocked. The callback previously caught all exceptions without a server log. The new safe `[pcss-auth] sign-in failed` runtime event records only the action, stage, error category, and an allowlisted OAuth error code; it excludes the authorization code, state, tokens, cookies, URLs, and raw provider description. After deploying it, reproduce **one** new sign-in and filter Vercel Runtime Logs for `/api/auth/callback` and `[pcss-auth]` at that time. `state-mismatch` points to a changed/lost callback query or competing flow; `flow-cookie-missing` points to host/cookie handling; `provider-authorization-error` points to Google returning an error; `token-exchange` with `invalid_client` points to a client ID/secret mismatch, while `invalid_grant` points to a consumed/expired code or callback-URI inconsistency. `identity-validation` points to issuer, nonce, signature, or claims validation. Do not rotate secrets or weaken state/nonce checks without that evidence.

**Confirmed token endpoint rejection:** The Production callback logged `phase: token-exchange`, `kind: provider-response`, `status: 401`, and `providerCode: invalid_client`. Google defines this as failed client authentication, such as an invalid client ID or secret or the wrong OAuth client type. The app's `openid-client` call uses the documented `ClientSecretPost` method, and the local token-exchange test verifies that it sends both fields. The next operator action is to open **Google Auth platform → Clients**, select the intended **Web application** OAuth client, and copy its client ID and current secret into the matching **Vercel Production** `OIDC_CLIENT_ID` and `OIDC_CLIENT_SECRET` variables. Make sure they come from the *same* client and are entered without extra quotes or whitespace. Leave `OIDC_CLIENT_AUTH_METHOD` unset (the default is `post`) or set it explicitly to `post`. Keep `OIDC_APP_ORIGIN=https://pcssclubs.org` and the authorized Google redirect URI `https://pcssclubs.org/api/auth/callback`. Redeploy Production so the variables reach the functions; a dashboard edit alone does not change an already-running deployment. Try one fresh sign-in. The UI now treats this particular rejection as a portal setup issue and points visitors to public browsing and the portal team instead of offering a futile retry.

**Build-gate correction:** Vercel reports `pcssclubs.ai-aarti.com` as `VERCEL_PROJECT_PRODUCTION_URL` for this project, while the portal's published URLs, canonical metadata, and intended Google callback use `pcssclubs.org`. The system variable identifies one production domain, not necessarily the site's chosen sign-in host. Requiring equality blocked a valid `OIDC_APP_ORIGIN=https://pcssclubs.org` build. The preflight now checks the configured origin's shape and required credentials without equating those two domains. Sign-in still requires visitors to use the exact origin configured in `OIDC_APP_ORIGIN`.

Vercel environment changes affect only new deployments. A failed build leaves the previous deployment and its previous variables live, even when the dashboard now shows the corrected Production value. After the build-gate correction is pushed, deploy it successfully, then check `/api/auth/session` again. The origin-mismatch JSON now includes only the public `requestOrigin` and `configuredOrigin` addresses, which can distinguish an old deployment from a proxy/host-forwarding mismatch without exposing credentials.

## Fixes in the repository

- Signed-out navigation keeps **Sign in**. Clicking it checks the session again, shows **Checking sign-in…** while that check runs, and prevents duplicate starts.
- The client now recognizes `ORIGIN_MISMATCH` (and the earlier error text) and explains that the portal team must correct the site setting. It stops offering a futile retry for that specific error and keeps public browsing and direct contact available. Other transient failures still offer retry and a persistent result message.
- `npm run build` runs `check:production-auth` first. On Vercel Production, it rejects missing or malformed OIDC settings and an HTTP/localhost app origin. It does not equate Vercel's automatically selected production URL with this site's chosen sign-in domain. The check prints setting **names**, never secret values. Preview and local builds remain unaffected.

## Operator recovery

1. In **Vercel → Project → Settings → Environment Variables**, set the **Production** value of `OIDC_APP_ORIGIN` to exactly `https://pcssclubs.org` (no trailing path). Check the other four required OIDC variables are present. Keep credentials and the session secret in Vercel environment variables, never in Git. A valid local `.env.local` does not supply Vercel Production.
2. In the Google OAuth web client referenced by `OIDC_CLIENT_ID`, register the exact callback `${OIDC_APP_ORIGIN}/api/auth/callback`. Confirm the Google application's audience and school Workspace access policy separately. The production build check validates local shape, not Google ownership or access policy.
3. Redeploy after changing Vercel variables. Vercel applies variable changes only to new deployments. Confirm `/api/auth/session` returns `configured: true`, then start sign-in from the site with a PCSS account and confirm the callback returns to My space. Test an unauthorized account and sign-out separately.
4. If the build fails with a named missing variable, set that variable for **Production** and redeploy. If the build passes but the session endpoint fails, inspect the deployment's auth-function logs and compare the requested host with `OIDC_APP_ORIGIN`. Do not send credentials, complete Google sign-in URLs, or authorization codes in a support request.
